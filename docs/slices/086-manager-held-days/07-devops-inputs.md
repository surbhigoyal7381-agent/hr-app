**Answer first.** No new container, queue or volume is needed. **The risk is one long web request, not load.** Nothing in this slice is measured yet; every number below is an estimate.

**What the code does today (fact, read):**
- The manager's list already exists: `team_days`. It reads every Attendance row for the team in the period, reads punches for them, and works out flags in Python. Paging happens **after** that read, so a page of 50 still costs the whole read. The period is capped at 92 days.
- A manager already files one request for one report: `raise_for_report`. Each one is a single draft insert. **Filing does not touch the salary slip.** The slip is re-saved only when HR submits the request (`release_by_hr`, inline, one full slip save per request).
- The monthly limit skips any request that carries a missing time (`enforce_monthly_limit` returns early), so held-day requests are not bounded by it.
- Acting stops at **direct** reports (her rule, 17 Oct). Viewing can be the whole line.

**Red flags for the brief (not mine to decide):**
1. **Scope conflict.** The founder says "all of their reporting employees". Her rule of 17 Oct is that acting stops at **direct** reports. Viewing the whole line is fine; bulk filing for skip-level staff would reverse that rule. Owner: `hrms-product-manager` / Surbhi. Default: list the whole line, file for direct reports only.
2. **One missing time for many days.** A held request carries a missing time and which punch is missing, per day. A bulk action that applies one time to many days writes guessed data into pay. Owner: UX and PM. The shape of the screen decides this.
3. **Pay effect at scale.** A manager's click only creates requests; HR's approval changes pay. Keep that split, or the 085 rule "nobody decides a request they raised" is lost.

**Run cost:** estimate, not measured: no new infrastructure, no new storage beyond N small Attendance Request rows (about 355 held days in the first half of November at DTC, so a few hundred rows a month). Extra CPU is the slip saves on approval. Negligible against the budget if refreshed once per employee; noticeable only as one slow request if done inline for 100 rows.

**Unknowns (could not check):** real time of one request insert; time of `refresh_draft_slip` on the heaviest DTC slip; gunicorn worker timeout; whether DTC managers share an office IP; Email Queue and job-queue state.

**Subtract pass:** removed a proposed held-days report, a new index, a background-job-by-default plan, a rate-limit change in nginx and any monitoring addition. Nothing else. Rung: reuse `team_days` and `raise_for_report` with a filter and a list-taking wrapper; no new code surface beyond that.

**Answer first.** No new container, queue, volume, nginx rule or migration. **One real risk: the send is one long request that may be cut off after some rows are filed.** The requirements below make that safe. **Facts that shape this (read, not run):** v2 has one day at a time, one reason per row (no shared note), the cap of 50 per send, and "answer lost" wording that reuses 085 AC-30. `raise_for_report` takes one employee and one date per call and files one draft. 087 changes it (reason required, Confirm flag) and 087's `send` is own-record only, so 086 must **not** call `send`.
