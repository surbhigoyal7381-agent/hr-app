# DevOps notes on the top priority candidates

**I advise. I decide nothing and I deploy nothing.** Every row below ends in a Decision
column that is yours to fill in.

## Read this first — the finding that should change the priority order

**C1 is not "documented, unenforced." It is built, wired up, and already on `dev`.**

The kano-review says `KPI.py` is "an empty `pass` controller" and that the
weightage-must-total-100 rule "is enforced nowhere." I read the file it names
(`alvoraa_goals/alvoraa_goals/alvoraa_goals/doctype/kpi/kpi.py`) — that one file really is
empty, which is normal for a Frappe doctype file; the logic lives in a controller module
instead. I also read `alvoraa_goals/alvoraa_goals/controllers/kpi.py`, which is 212 lines
and does exactly what C1 asks for:

- `_validate_weightage_budget()` sums an employee's KPI weightages for one cycle and
  throws if the total would pass 100% (`TOTAL_WEIGHTAGE = 100.0`).
- `refuse_rating_changes()` stops a rating being written on the live KPI at all — ratings
  now live only on a review's own copy (built for slice 010).
- Direction-aware attainment (`Lower is Better` vs `Higher is Better`), a non-zero target
  check, and a status engine are all there too.

And it is wired: `alvoraa_goals/alvoraa_goals/hooks.py` line 34 registers
`validate_kpi` (which calls `_validate_weightage_budget`) as the KPI doctype's `validate`
hook. **I checked this is not local, uncommitted work**: `git diff origin/dev -- <file>`
returns nothing, and `git merge-base --is-ancestor 7a2b4be origin/dev` confirms the commit
that carries this code is already an ancestor of `origin/dev`. It shipped as part of
slice 010's group D work (the comment in the file says so: "slice 010 group D: SEC-2,
R13, PRIV-9").

**What this means for the priority order:** C1, ranked #3 with an S–M effort estimate for
work "not yet built," needs almost no new engineering. What is left is smaller than the
kano-review assumed — see OPS-1 below. **The PM should re-check §1 and §3 of the
kano-review against this before the priority order is finalised**, since the "wrong
numbers before new numbers" risk this candidate was meant to close is already closed for
the weightage case.

## 1 · C11 — push slice 010 to `dev`, then `main`

**Short answer: ready to recommend for `dev`.** The rehearsal on `ppj.localhost` (a copy
of a real PP Jewellers dataset, not synthetic seed data) already did the hard part: it
found two release blockers and proved both are fixed. Local build/test is thorough
(1,128 + 18 tests, plus 14 pin tests proving each fix is actually guarded).

### What's actually true about the deploy pipeline today — and where `DEPLOYMENT_RUNBOOK.md` is now wrong

`DEPLOYMENT_RUNBOOK.md` (18 Aug 2026) says "one bench, four sites" and that an automatic
deploy workflow exists but never fires because `secrets.DEPLOY_HOST` is unset. **That is
stale.** The current `.github/workflows/deploy.yml` is a different, later design:

- **`dev` is its own stack** (`docker-compose.devstack.yml`, its own MariaDB, its own
  `sites` volume, project name `devstack`) — separate from the `compose` project that
  serves `alvoraa.co`. Pushing to `dev` no longer swaps production's image or database.
- **Deploys are automatic on push** for `dev` and `test`. **`main` also deploys
  automatically after Build Image succeeds, but is gated by a GitHub Environment
  approval** (`environment: production`, comment says "Required reviewers" must be
  configured) — I could not confirm from the repo alone whether that reviewer rule is
  actually turned on in GitHub's settings; that is a live setting, not a file. **Recommend
  confirming it before this or any future push to `main`.**
- Backups (`bench --site all backup --with-files`, all sites, before anything changes),
  the nginx-config gate (`scripts/check_nginx_parses.sh`, closes the class of outage slice
  019 was written for), maintenance mode per site (looped, not the broken `--site all`
  form), retries on a flaky registry pull, and a cleanup trap that restores service even
  on failure, are all already built into this workflow. This is a mature pipeline; slice
  010 does not need a bespoke deploy procedure.

### Is there a migration, and what does it do

Yes. Two of the four patches seen in the `ppj.localhost` rehearsal are slice 010 group D's:
`alvoraa_goals.patches.v1_0.take_review_copies` and
`alvoraa_goals.patches.v1_0.stamp_lock_release_days`. The other two
(`fill_branch_on_hr_records`, `make_evidence_files_private`) are earlier slices' patches
that dev tenants should already have applied — so **the real `dev` migration should run
only 2 patches, not 4**, and should be faster than the 101 seconds measured on
`ppj.localhost` (which itself included a ~25 s wait on another open connection, not a
defect). **Recommend confirming dev's Patch Log already has the other two patches before
assuming this** — a five-minute read-only check, not a deploy action.

The migration is a **copy, not a rewrite**: it takes a per-review snapshot of each KPI and
Objective into a new `Alvoraa Review Item` row. It does not touch the live KPI or
Objective records. That is what makes the rollback story survivable (below).

### Rollback

`deploy.yml`'s own rollback note is right for this release: **a migration ran, so rolling
back means redeploying the previous image tag *and* restoring the pre-deploy backup** —
Frappe patches are not reversible in place. Two extra things specific to this slice,
found in the rehearsal and not in the generic runbook:

- **Do not run `undo_backfill` on a tenant that may get group D again.** The patch is
  recorded in the Patch Log, so a later re-release will skip Completed reviews on
  first-open and their copies will not come back. If a real rollback is ever needed,
  restore-from-backup is the safe path, not the repair script.
- **Stop people using reviews before any rollback step runs.** Ratings given in the
  portal between the rollback decision and the image swap are not carried backward by
  `copy_ratings_back_for_rollback` for reviews completed after go-live (this was found
  and then fixed for the *forward* case — F5 — but the rollback window itself still needs
  a short freeze, which the checklist does not currently say).

## 2 · C7 — the fate of the unused PMS module vs `alvoraa_goals`

**This is bigger than "an unused module" — it is a stated, deliberate product decision
that current CI already enforces, and it adds real, live, running cost to every tenant
the moment the current `Dockerfile` is what builds the image.**

### What I found that the kano-review did not have

`ARCHITECTURE.md` §11, read directly, is blunt about it:

> "Per the product decision, **all modules ship enabled in production**... The first
> `bench install-app hrms` **creates 37 new tables** and activates untested permission
> handlers, document hooks and web routes (`/pms-employee`, `/pms-manager`,
> `/pms-calibration`, `/pms-steering`)... **Enabling both is the stated intent** — just be
> aware users will see two routes to similar functionality."

So "decide the fate of the PMS module" is not a green-field decision — it is a decision
to **overturn** a documented one. Three concrete, operational facts follow from that:

1. **Scheduled jobs already run against it, on every tenant, whether or not anyone uses
   it.** `hrms/hrms/hooks.py` registers `hrms.pms.pms_notifications.process_notification_queue`
   hourly and `send_overdue_stage_alerts` / `send_checkin_nudges` daily. These run on the
   shared `default,short` worker (`docker-compose.app.yml`). At zero PMS records the query
   cost is near-nothing, but it is still one more job that can error, write to Error Log,
   and hold a worker slot — and it is code that, per ARCHITECTURE.md's own words, "has
   never executed against any database" in production.
2. **Web routes exist and are reachable**: `/pms-employee`, `/pms-manager`,
   `/pms-calibration`, `/pms-steering`. If the module is enabled, these are public-facing
   pages built on permission handlers ARCHITECTURE.md itself calls "untested." That is a
   security-review question, not just a tidiness one — flag to the security engineer
   regardless of which way C7 is decided.
3. **CI already gates on it existing**, not on it being *correct*: `.github/workflows/ci.yml`
   installs `hrms` on a fresh site and asserts `DocType` rows exist for module
   `Performance Management` (lines ~277–295). It does **not** run any functional test suite
   against PMS — `bench run-tests` in that workflow only covers `alvoraa_goals` and
   `alvoraa_portal`. So today's CI proves the *schema* loads, and proves nothing about the
   *behaviour* of 37 doctypes, 137 files, and four public-facing routes.

### Two paths, and what each actually costs to run

| Path | What it costs operationally |
|---|---|
| **Keep enabled, as the stated intent says, and actually exercise it** (ARCHITECTURE.md §12's own action item 6: "Exercise the PMS module in dev... before promoting") | New functional test coverage to write (currently zero); the four routes need a security pass before being trusted with real employee data; the two hourly/daily jobs need to be proven safe at scale, not just present; ongoing double-maintenance of two performance systems, which is exactly the "confused users, support tickets" risk the kano-review names |
| **Disable it** (hide the module from the UI/workspace, do not remove the tables) | Reverses a written product decision — needs the founder's sign-off, not just an engineering call. `scripts/check_app_integrity.py` (our own integrity gate) **only checks `alvoraa_goals` and `alvoraa_portal`** — it does not check `hrms`, so hiding or touching PMS doctypes inside the `hrms` fork is **not covered by our own CI safety net**. `nfr-budget.md` §9 separately states "`apps/frappe`, `apps/erpnext` and `apps/hrms` are never edited... that is an escalation, not a coding decision" — which is in direct tension with `deploy/Dockerfile`'s own comment that `hrms` is a first-party, vendored fork copied out of this repo (not `bench get-app`-installed). That tension needs resolving before anyone edits `hrms/hrms/performance_management` at all |

### Whether this is actually live today, right now

**I don't know, and I did not check dev or production to find out** — that would be a
dev-stage read, and the task here is repo-only analysis. What I can say from the repo:
the current `deploy/Dockerfile` (the one that would build the *next* image) `COPY`s the
real `hrms` fork including its `pms/` and `performance_management/` directories, so the
**next** image built from this Dockerfile will create the 37 tables on `install-app` /
`migrate`, on every site, the moment it deploys. Whether the *currently running* image on
`dev` or `alvoraa.co` already does this depends on when it was last built and deployed,
which I have not been asked to check. **Recommend someone confirm this with a read-only
`bench --site <site> execute` doctype count**, the same one-liner ARCHITECTURE.md uses,
before treating C7 as hypothetical.

## 6 · C3 — Rating Derivation + plain-language explanation

**Not built, and this is the one candidate where slice 010 quietly did some of the
groundwork already.** `Alvoraa Review Item` (`alvoraa_goals/alvoraa_goals/alvoraa_goals/doctype/alvoraa_review_item/`)
already stores a per-review, point-in-time copy of each KPI/Objective — the exact shape a
"replayable" derivation needs (what the numbers were, at the time, for this review). C3
does not have to invent that snapshot mechanism from nothing; it can very likely build the
explanation layer on top of the copies slice 010 already writes.

**Storage and replay implications, since this stores a snapshot per rating:**

- **It grows without bound if not managed.** `nfr-budget.md` §1 treats this class of data
  ("KPI Facts") as the single biggest table in the system and says explicitly:
  **append-only, 36 months online + archive, partition it.** The same discipline should
  apply to review-item snapshots once C3 adds an explanation layer on top of them —
  decide the retention and partitioning plan in the same slice that builds C3, not after.
- **It is exactly the control the AI Act's Article 86 (right to an explanation) and GDPR
  Article 22 want**, per `security-compliance-baseline.md` §4: "the product answer to
  Art 86 is already specified: FR-G4 (replayable Rating Derivation) plus FR-G5
  (plain-language explanation) plus FR-J5 (AI action log)." If EU exposure is ever
  confirmed (still an open question in that baseline), C3 stops being a differentiator and
  becomes the compliance answer — worth flagging to the PM as a reason not to let it slip
  indefinitely.
- **Minimum-necessary applies.** `security-compliance-baseline.md` §2 requires data
  minimisation; the snapshot should hold what's needed to explain the number (weights,
  attainment inputs, the rating scale applied), not a copy of every field on the source
  documents.
- **No new background job is obviously required** — the explanation can likely be computed
  on read from the stored snapshot, not pre-generated. If a plain-language narrative is
  AI-assisted, that is governed entirely by §6 of `nfr-budget.md` (AI never sets a rating,
  narrative comes only from that employee's own record, every AI action logged, a
  non-AI fallback exists) — none of that changes because of this candidate specifically,
  but it applies the moment "plain-language explanation" is AI-generated rather than

## 10 · C10 — Tally/Zoho/CRM adapters (outbound polling integrations)

**Not built. This is the one candidate on this list that genuinely needs new
infrastructure decisions, not just new screens on existing plumbing.** I searched for any
existing outbound-integration pattern (`import requests`, `frappe.integrations`, OAuth,
`make_post_request`) in `hrms`, `alvoraa_goals` and `alvoraa_portal` and found **none in
application code** — this would be the first outbound integration in the product.

What already exists to build on: a `long` queue (`worker-long`) separate from
`default,short` (`worker-default`), and an established `frappe.enqueue(..., queue="long",
deduplicate=True, job_id=...)` pattern already used for at least one recurring job
(`alvoraa_portal/data_review.py`). That pattern — named job IDs, deduplication — is the
right shape to reuse for polling jobs; it is not the right *queue* to reuse without
thinking it through (below).
